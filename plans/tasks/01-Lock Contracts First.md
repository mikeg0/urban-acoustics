# 01 - Lock Contracts First

## Goal

Define the Phase 1 device-to-cloud contracts before implementing services. This prevents the Pi firmware, MQTT ingest worker, REST API, simulator, and frontend from each inventing slightly different payload shapes.

Phase 1 is considered contract-ready when all telemetry, health, event, command, identity, and environment interfaces are documented and validated by shared schemas or fixtures.

## Scope

- Define MQTT topic names and direction.
- Define JSON payload schemas for all Phase 1 messages.
- Define REST request/response schemas for event upload, telemetry reads, labels, and device metadata.
- Define the event lifecycle and valid state transitions.
- Define device identity fields and certificate fingerprint semantics.
- Define backend/runtime environment variables.
- Add golden fixtures for simulator, ingest, and backend tests.

## Deliverables

- `plans/phase-1-contracts.md`
- `backend/app/contracts.py` or equivalent Pydantic schema module
- `backend/tests/fixtures/` with valid and invalid sample payloads
- Topic and endpoint table covering:
  - `dev/{device_id}/tlm`
  - `dev/{device_id}/health`
  - `dev/{device_id}/event/announce`
  - `dev/{device_id}/event/done`
  - `dev/{device_id}/cmd/+`
  - `dev/{device_id}/lwt`
  - `POST /api/v1/events/intent`
  - `GET /api/v1/events/{id}`
  - `GET /api/v1/devices/{id}/telemetry`
  - `POST /api/v1/events/{id}/labels`

## Contract Details

### Telemetry

Minimum payload:

```json
{
  "ts": 1745673600.123,
  "laeq": 58.4,
  "lafmax": 67.2,
  "lcpeak": 82.1
}
```

Rules:

- `ts` is Unix epoch seconds with millisecond precision allowed.
- `laeq`, `lafmax`, and `lcpeak` are dB values.
- Device ID comes from the MQTT topic, not the payload.
- Unknown fields may be tolerated for forward compatibility, but required fields must fail validation when missing.

### Health

Minimum fields:

- `ts`
- `uptime_s`
- `cpu_pct`
- `cpu_temp_c`
- `mem_used_mb`
- `disk_free_mb`
- `wifi_rssi_dbm`
- `queue_depth`
- `queue_bytes`
- `mic_gain_db`
- `ntp_offset_ms`
- `fw_version`
- `config_version`

### Event Announce

Minimum fields:

- `event_id`
- `ts`
- `duration_s`
- `peak_db`
- `sha256`
- `size`
- `content_type`

Rules:

- `event_id` is generated by the device as a UUID.
- `sha256` is the FLAC file hash.
- `size` is byte length before upload.
- Announce must be idempotent.

### Event Done

Minimum fields:

- `event_id`
- `storage_key`
- `sha256`
- `size`
- `uploaded_at`

Rules:

- Backend verifies the event exists and hashes/sizes match the intent metadata where possible.
- Duplicate done messages must not create duplicate events.

### Event Lifecycle

Valid states:

- `announced`
- `upload_intent_created`
- `uploaded`
- `available`
- `failed`

Required behavior:

- Repeated announces for the same `event_id` return or preserve the existing row.
- Repeated done messages for an uploaded event are idempotent.
- Failed upload attempts can return to `upload_intent_created` if the device retries.

## Dependencies

- None. This task should be completed before backend, ingest, simulator, and Pi implementation.

## Acceptance Criteria

- All Phase 1 payload examples validate against shared schemas.
- Missing required fields fail with clear validation errors.
- Invalid numeric values are rejected or normalized according to documented rules.
- Topic naming is consistent across plan, schemas, simulator, and MQTT ACLs.
- The contract document identifies which fields are stable and which are forward-compatible extension points.

## Notes

- Keep contracts boring and explicit. This is infrastructure for debugging real devices in the field.
- Do not include Phase 2 live stream contracts here.
